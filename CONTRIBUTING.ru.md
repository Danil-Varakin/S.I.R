# Как участвовать

> English version: [CONTRIBUTING.md](./CONTRIBUTING.md)

Как работать над Sir. Обоснование дизайна — в [ARCHITECTURE.md](./ARCHITECTURE.md)
(англ.), правила версий — в [VERSIONING.md](./VERSIONING.md).

## Что нужно

- **Node 22+.** Исходники — `.ts`, исполняются напрямую через
  `node --experimental-strip-types`: для разработки сборка не нужна. `npm run build`
  (`tsconfig.build.json` → `dist/`) нужен только для пакета.
- `npm install` ставит три рантайм-зависимости: `web-tree-sitter` (WASM-грамматики —
  кросс-платформенно, без компилятора и `node-gyp`), `diff` (построчный diff под
  `generate`) и `simple-git` (чтение версии из git).
- Грамматики грузятся асинхронно: адаптер отдаёт `init(): Promise<void>`, его ждут один
  раз на старте, после чего `buildMap` синхронный. Всё, что вызывает `buildMap`, —
  включая тесты — обязано сначала выполнить `await adapter.init()`.

## Запуск и проверки

```bash
npm test           # node --test по test/**/*.test.ts
npm run typecheck  # tsc по src/, test/ и bench/ (три конфига)
npm run check      # то и другое — перед каждым коммитом
npm run bench      # замеры скорости (bench/); в check не входит
```

Команды запускаются прямо из исходников:

```bash
npm run sir -- <команда> …
npm run apply -- --match changes.sirp --in src/main.cpp --out out.cpp
npm run generate -- --in new.cpp --in-old old.cpp --debug
npm run service    # сервис JSON-строк, PROTOCOL.md
```

Красный `npm run check` блокирует коммит.

## Строгий tsconfig

У каждого флага своя причина; без причины флаги не ослабляются:

- **`noEmit` + `allowImportingTsExtensions`** — `tsconfig.json` только проверяет типы;
  исходники исполняются через strip-types, поэтому импорты пишутся с расширением `.ts`.
  Сборка пакета (`tsconfig.build.json`) включает вывод и добавляет
  `rewriteRelativeImportExtensions`, который переписывает `.ts` → `.js` в результате.
- **`verbatimModuleSyntax` + `isolatedModules`** — импорт только типов ОБЯЗАН быть
  `import type { … }`: типы из `ast.ts` импортируются через `import type`, а значение
  `ParseError` — обычным `import`.
- **`noUncheckedIndexedAccess`** — доступ по индексу (`arr[i]`, `m.groups[k]`) даёт
  `T | undefined`. Это обрабатывается явно: `?? ''`, `.entries()`, проверка или `!` там,
  где значение гарантирует инвариант.
- **`exactOptionalPropertyTypes`** — `hint?: string` НЕ включает `undefined`; поле
  присваивается, только когда значение есть (`if (hint !== undefined) …`). Если объект
  опций законно получает вычисленное `T | undefined`, расширяется это одно поле до
  `T | undefined`, а не флаг.

## Соглашения по коду

- **Никаких parameter properties в конструкторах** — strip-types их не поддерживает.
  Поля объявляются явно (см. `core/errors.ts`).
- `core/` остаётся языконезависимым: ни одного `case '}'`, никаких правил отступов,
  никакого импорта tree-sitter. Правка «для C++» или «для Python» — в папке этого языка
  в `lang/`.
- Новый язык никогда не означает правку `core/`: одна папка в `lang/` и две строки в
  реестре `lang/adapter.ts`. Реестр — закрытый whitelist: имя языка из `.sirp` никогда
  не превращается в динамический `import()`. Правило одной папки на язык — в README,
  «Как добавить язык».
- Комментарий объясняет **почему**, а не что. Комментарий, пересказывающий код, — шум;
  комментарий, который называет отказ, предотвращённый строкой, оправдывает своё место.
- Инвариант, который может нарушить баг, бросает исключение, а не тихо даёт
  `undefined`: плохой индекс, молча ставший «всем файлом», всплывает через три модуля.
- Файлы пишутся атомарно (`infra/fs.ts`): временный файл, затем `rename`. sir правит
  исходники, и обрезанный файл — сломанная сборка.
- Ошибки наследуют `SirError` и несут `exitCode`. Сообщения пользователю — на
  английском и говорят, что делать дальше.

Где какой каталог и файл и что в нём — README, «Структура проекта». Какой файл владеет
каким правилом — ARCHITECTURE.md, «Where each rule lives».

## Тесты

- `test/unit/` — файл на модуль и проверки самих правил: `versioning.test.ts`
  (VERSIONING.md), `protocol-types.test.ts` (типы провода против ядра), `api.test.ts`
  (экспорты против раздела «API» в README), `property.test.ts` (свойства на
  сгенерированных входах).
- `test/roundtrip/` — `parse(print(ast))` ≡ `ast`.
- `test/golden/<язык>/` — случаи, написанные вручную, ниже.

Соглашения:

- Тест проверяет **поведение вместе с причиной**, причина пишется в комментарии. Если
  тест существует из-за конкретного бага, это указывается, чтобы проверку потом не
  «упростили».
- Для конвейеров предпочтительны сквозные проверки: породить ханки, применить их,
  сравнить с ожидаемым файлом. Так ловится взаимное влияние ханков, которое проверки по
  модулям пропускают.
- Исправление бага приходит с минимальным входом, который его воспроизводит, и тест
  прогоняется на старом коде, чтобы убедиться, что он падает.

Инварианты из
[ARCHITECTURE.md](./ARCHITECTURE.md#diagnostics-and-invariants-green-on-every-commit)
зелёные на каждом коммите.

### Golden-случаи

В `test/golden/<язык>/` две папки, и проверяют они разное:

- **`generate/`** — `test<n>.old.<расш>` и `test<n>.new.<расш>`. Каждый случай
  синтезируется, печатается, разбирается, применяется к старому файлу и сравнивается с
  новым (результат верен), а напечатанный `.sirp` сравнивается байт в байт с
  `test<n>.sirp` (форма та же). Round-trip ничего не говорит о форме: ханк, переписавший
  всё тело функции, воспроизводит файл так же точно, как однострочный. Изменение формы не
  ломающее, но идёт в CHANGELOG (VERSIONING.md F1).
- **`apply/`** — `test<n>.sirp`, применённый к `test<n>.<расш>`, обязан дать
  `test<n>.expected.<расш>`. Так держится VERSIONING.md F1: выпущенный `.sirp` обязан
  применяться одинаково во всех следующих релизах, поэтому изменившийся ожидаемый
  результат — ломающее изменение, если старый не был багом. Те же случаи прогоняются через
  каждый бинарник `sir-apply`.

Когда изменение НАМЕРЕННО меняет ожидаемый результат, он перегенерируется, и **diff
читается**:

```bash
UPDATE_GOLDEN=1 npm test
```

Две метки, в первой строке случая:

- `MUST-REFUSE` — патч НЕ должен лечь. Тихое ложное совпадение — худший класс багов,
  какой может быть у sir, поэтому на него есть тест.
- `KNOWN-GAP` — синтез пока этого не умеет. Когда научится, тест упадёт с «уберите
  метку».

S.I.R также прогонялся на настоящих файлах Chromium с настоящими downstream-патчами.
Это сторонний код под сторонней лицензией, в репозиторий он не входит; `test/golden` —
набор, который может запустить каждый.

## Перед pull request

1. `npm run check` зелёный.
2. У исправленного бага есть тест, который **падает без исправления**. У новой
   возможности есть golden-случай или property-тест: пример закрепляет один вход, golden
   или свойство держат поведение на входах, которых никто не писал.
3. Изменение публичного поведения отражено в `README.md` **и** `README.ru.md`, а
   `--help` CLI говорит то же, что README.
4. Изменение контракта — протокола, схемы конфига, формата `.sirp`, флагов CLI —
   поднимает свой номер, как требует VERSIONING.md, и имеет строку в разделе «Unreleased»
   `CHANGELOG.md`.
5. Сообщение коммита говорит, *почему*, а не только *что* изменилось.

## Грамматики

В git грамматик нет. `npm run grammars` (`scripts/fetch-grammars.ts`) кладёт закреплённые
в `grammars/`, каждую сверяя с её sha256; файл, который уже лежит с верными байтами, не
трогается. Его запускают `npm test` (`pretest`) и `npm pack` (`prepack`), поэтому первый
прогон тестов в свежем клоне требует сети (CDN npm: jsdelivr, затем unpkg). Сам sir
ничего не скачивает.

`SIR_GRAMMAR_DIR` заставляет sir сначала искать в другой папке — для работы над ядром
или своей грамматики; пин всё равно проверяется.

## Релиз

**[VERSIONING.md](./VERSIONING.md) обязателен**: какой номер когда меняется, что считается
ломающим, шаги релиза (§5). У каждого релиза есть запись в [CHANGELOG.md](./CHANGELOG.md)
до тега.

Релиз выпускает CI. Последний шаг §5 пушит тег:

```bash
git push origin v<версия>
```

После этого `.github/workflows/release.yml`:

1. сверяет тег с `version` в `package.json` — тег на коде с прежней версией отклоняется;
2. запускает typecheck и тесты;
3. запускает `npm pack` (`prepack` кладёт грамматики и собирает `dist/`);
4. собирает `sir-apply` для linux-x64, linux-arm64, darwin-arm64 и win-x64 и прогоняет
   через каждый бинарник apply-голдены и `test/unit/sir-apply.test.ts`;
5. пишет `SHA256SUMS` и публикует GitHub Release с `.tgz`, бинарниками и суммами. В реестр
   npm не уходит ничего.

Перед тегом запускается mutation-workflow (или `npm run mutation`). Счёт ниже прошлого —
повод посмотреть, что тесты перестали ловить, а не блок релиза.

Собрать архив локально (`npm run check`, затем `npm pack`), ничего никуда не отправляя:

```bash
npm run pack
```

Посмотреть список файлов, ничего не создавая:

```bash
npm pack --dry-run
```

В архиве — `dist/`, `grammars/`, `schemas/`, `sir.config.schema.json`, оба README,
`PROTOCOL.md`, `LICENSE` и `package.json`; решает поле `files` в `package.json`. Ничего из
`src/`, `test/` и `docs/`.

Как пользователи ставят каждый вид sir — README, «Установка».

## Проверки (CI)

`.github/workflows/ci.yml` запускается на каждый push и pull request:

- **матрица** — Linux, macOS и Windows, каждая на всех версиях Node, которые
  поддерживает проект (список — в `ci.yml`). `grammars/` кешируется между запусками, ключ —
  пины в `src/lang/*/index.ts`;
- **покрытие** — код пакета (`src/`) не ниже 98 % строк и 95 % ветвлений. В
  `npm run check` не входит: покрытие замедляет набор, которого ждёт каждый коммит.
  Локально:

  ```bash
  node --test --experimental-strip-types --experimental-test-coverage --test-coverage-include='src/**' --test-coverage-lines=98 --test-coverage-branches=95 "test/**/*.test.ts"
  ```

- **состав пакета** — собирает пакет, проверяет, что в архиве есть грамматики, и ставит
  его так, как велит README (`npm run smoke:install`): команда, API и сервис;
- **sir-apply (linux-x64)** — собирает бинарник и прогоняет через него apply-голдены и
  его тесты, чтобы импорт, который не собирается в бандл, нашёлся до релиза.

`.github/workflows/nightly.yml` каждую ночь прогоняет property-тесты на новом seed, в 25
раз больше случаев, чем `npm test` (и вручную: *Run workflow*, с seed, чтобы повторить).
Упавший случай называет свой seed; сводка запуска даёт команду, которая вытянет те же
случаи:

```bash
SIR_PROP_SEED=<seed> SIR_PROP_RUNS=25 node --test --experimental-strip-types test/unit/property.test.ts
```

Упавший seed — такой же баг, как любой другой: его исправляют и добавляют случай отдельным
тестом. Seed — не тест: генератор свойства может измениться.

`.github/workflows/mutation.yml` раз в неделю и вручную запускает `npm run mutation` —
Stryker (`stryker.config.json`) по `core/` и синтезу: доля подброшенных багов, которые
ловят тесты. Он инкрементальный: после первого прогона заново идут только мутанты, чей код
или тесты изменились. Эта проверка смотрит на сам мутированный код и покрывающие его
тесты, но не на код вокруг: после правки, которая меняет смысл мутанта — рядом убрана
охрана, например, — берётся результат, который уже неверен. После такой правки прогон
целиком: `npm run mutation -- --force`.

Сравнимы только прогоны на ненагруженной машине и на одном стенде (машина, Node,
`concurrency`, конфиг). Stryker считает таймаут пойманным мутантом: нагрузка завышает
счёт, и даже на свободной машине он гуляет на таймаут-другой. Рабочих процессов — не
больше ядер: `mutation.yml` даёт 4-ядерному раннеру 4. Оценки, стенды и длительность
прогонов — в `docs/BACKLOG.md`, раздел «М».

Мутант, который никогда не меняет результат, — прежде всего повод упростить код: проверка,
которая ничего не решает, уходит. Только где упростить нельзя, он помечается на месте,
`// Stryker disable next-line <mutator>: <why>`, — и только если все мутации этого вида в
строке эквивалентны: пометка выключает их все, и пойманные тоже (`<`, у которого `<=`
ничего не меняет, а `>=` ловится, не помечается).
