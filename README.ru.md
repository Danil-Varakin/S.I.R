# Hatch

**Структурные семантические патчи для исходного кода.** Вместо хрупких номеров
строк патч Hatch описывает, *где* менять код, в терминах самой структуры кода — а
инструмент находит место. Порт оригинального Python-прототипа на TypeScript:
типизированный AST и npm-нативный пайплайн (без Python в сборке).

> English version: [README.md](./README.md)
> Архитектура: [ARCHITECTURE.md](./ARCHITECTURE.md) · Как участвовать: [CONTRIBUTING.ru.md](./CONTRIBUTING.ru.md)

## Зачем

Патчить быстро меняющийся upstream классическими `.patch`-файлами больно:
вставили пару строк выше — и номера строк во всех ханках поехали. Hatch описывает
изменение декларативно — «вставить вот это *после того include*, *внутри той
функции*» — тремя операторами. Позиция ищется по разобранной структуре файла,
поэтому переформатирование и несвязанные правки upstream патч не ломают.

Три команды:

- **`apply`** — применить `.hatch`-инструкции к исходному файлу.
- **`generate`** — сравнить две версии файла и породить `.hatch`-инструкции.
- **`init`** — создать `hatch.config.json` (см. «Конфигурация»).

`generate`, затем `apply` замыкают round-trip: применение порождённого патча к
старому файлу воспроизводит новый. `generate` гарантирует это по построению — он
применяет каждого кандидата настоящим патчером и оставляет только того, кто
воспроизвёл правку.

## Формат файла

Патч — это файл `.hatch`: шапка (её поля — в разделе «Шапка» ниже), затем пары блоков
`match`/`patch`:

```
Hatch: 1
Target: src/a.cc
Base-Blob: 3b18e512dba79e4c8300dd08aeb37f8e728b8dad
Hatch-Version: 0.5.0
Grammar: tree-sitter-cpp@0.23.4

# match <язык>
    <шаблон, каждая строка с жёлобом в четыре пробела>
# end
# patch
    <текст замены, тот же жёлоб>
# end
```

Блоки подчиняются трём правилам:

1. **Колонка 0 принадлежит структуре.** `# match`, `# patch` и `# end`
   распознаются только там.
2. **Каждая строка нагрузки несёт жёлоб в четыре пробела**, он снимается при
   чтении. Поэтому строка нагрузки физически не может попасть в колонку 0:
   ограда ` ``` `, заголовок `# patch` или `# end` внутри raw string — обычный
   текст. Разделителя, с которым код мог бы столкнуться, в формате нет вовсе.
3. **Блок закрывается `# end`.** Пустые строки внутри блока — нагрузка, включая
   хвостовые; пустые строки между ханками — нет. Текст между шапкой и первым
   `# match` незначащий: hatch его не читает.

У ханка может быть комментарий: блок `# note` … `# end` прямо перед его `# match`.
Заметка — произвольный текст в любой колонке, без жёлоба; её читают только люди, сопоставитель —
никогда; через сервис она приходит полем `note` ханка. Текст между ханками вне заметки —
ошибка разбора. `generate` заметок не пишет: повторный запуск поверх `.hatch` заменяет их
вместе со всем остальным.

```
# note
WAIT: без него драйвер зависает на полном буфере.
# end
# match c
    ...
```

Строка нагрузки без жёлоба — ошибка разбора, а не тихая потеря. Единственное
исключение, которое стоит знать: строка со **значащими хвостовыми пробелами**
неотличима от мусора для любого whitespace-fix, поэтому не прогоняйте файл
инструкций через такой инструмент — `generate` предупреждает, когда печатает
такую строку.

Окончания строк — не нагрузка. Файл инструкций может прийти с LF или с CRLF (git и
редакторы переводят их в обе стороны), читается он одинаково. Патч берёт окончание
строк того файла, в который ложится: в CRLF-файле каждая записанная им строка
кончается на CRLF, в LF-файле он ложится байт в байт. Если в файле окончания
смешаны, решает строка, с которой начинается правка.

### Шапка

Шапка — первые строки файла вида `Имя: значение`, до первой пустой строки, как в патчах
Debian (DEP-3). Она говорит, к какому файлу относится патч и чем он сделан; ханки идут
после пустой строки.

```
Hatch: 1
Target: chrome/browser/feature_list.cc
Base-Blob: 3b18e512dba79e4c8300dd08aeb37f8e728b8dad
Hatch-Version: 0.5.0
Grammar: tree-sitter-cpp@0.23.4
```

| # | поле | значение | когда `generate` его пишет | что с ним делает hatch |
|---|---|---|---|---|
| 1 | `Hatch` | номер формата `.hatch`, целое число; сейчас `1` | всегда | читает патч, только если номер в диапазоне, который знает этот hatch: патч новее — отказ «обновите hatch», старше — «перегенерируйте патч» |
| 2 | `Target` | файл, к которому относится патч: относительный путь через `/`, без `..`. Считается от корня `upstream`, если он задан в конфиге, иначе от корня репозитория | когда у патча есть место; не пишется при `--out -` и для патча вне репозитория | по нему `apply` без `--in` и `hatch-apply` находят файл, а расширение редактора переходит от патча к коду. Абсолютный путь или `..` — ошибка разбора |
| 3 | `Base-Blob` | идентификатор git-blob старой версии, против которой сделан патч | когда старая версия взята из git (`--head`, `--branch`, `--commit`, `generate.base`) | не проверяет — справочное поле. `git cat-file -p <Base-Blob>` печатает базу, на которую патч заведомо ложился |
| 4 | `Hatch-Version` | версия hatch, который написал патч: `0.5.0` | всегда | не проверяет — справочное поле |
| 5 | `Grammar` | грамматика tree-sitter, которой разобран файл: `<пакет>@<версия>` | всегда | не проверяет — справочное поле. Другая версия грамматики может разобрать код иначе, и по этому полю видно, какой был сделан патч |

Правила:

- `Hatch` — всегда первая строка. Остальные известные поля идут в порядке таблицы, каждое
  не больше одного раза; пропущенное поле не сдвигает остальные. Известное поле не на
  своём месте или повторённое — ошибка разбора (код 2).
- Имена полей читаются без учёта регистра, пробелы вокруг значения отбрасываются.
- Поля, которых hatch не знает, могут стоять где угодно после `Hatch` и пропускаются:
  в шапку можно дописать свои, например `Author:` или ссылку на задачу.
- Строка шапки не в виде `Имя: значение` — ошибка разбора: шапка кончается только пустой
  строкой.
- В патче, написанном вручную, обязательна только `Hatch`. Шапку можно не писать вовсе:
  такой файл читается как формат 1, и `apply` нужен `--in`.
- Новое поле добавляется только в конец таблицы (VERSIONING.md H4), поэтому шапку,
  записанную старым hatch, новый читает так же.

## Язык: три оператора

Блок `match` пишется на целевом языке, операторы вставлены между строками:

| Оператор | Значение |
|----------|----------|
| `...`    | пропуск до следующего якоря (перебираются все вхождения, с откатами) |
| `>>>`    | точка вставки |
| `<<<`    | конец диапазона замены (он начинается от `>>>`) |

Всё, что не оператор, — **якорь-литерал**, кусок целевого файла, который обязан
там быть. Шаблон описывает файл **целиком**: нет `...` перед первым литералом —
значит «с самого начала файла», нет `...` после последнего — «до конца файла».

Пробелы между литералами и операторами для скобочных языков незначимы, поэтому
якоря можно копировать из исходника и переотступать как удобно. Для Python — нет:
ведущий отступ строки нагрузки входит в якорь, поэтому многострочный якорь
закрепляет уровень каждой своей строки. Питоньи якоря копируйте из исходника
вместе с отступом.

**Внутри строкового литерала пробел — данные, и он значим.** `Log("a  b")` и
`Log("a b")` — разные якоря, второй на первом не сработает. Исключение —
МНОГОСТРОЧНЫЙ литерал (`R"(…)"`, докстринг, template literal, backtick в Go): внутри
него пробелы по-прежнему схлопываются. Причина в том, что якорь — фрагмент, отрезанный
по границам строк, и он может начаться внутри такого литерала, не имея возможности об
этом узнать; уравнять обе стороны можно только так.

Оператор распознаётся только как отдельное *слово* (пробел или край строки с
обеих сторон), поэтому `template <typename... Args>` остаётся литералом.
Настоящее обособленное `...` в коде экранируется как `\...`.

Оператор между двумя словами без `...` — `int foo >>> bar;` — означает тот один пробел,
что между ними: `bar` обязан идти за `foo` ровно через один пробел канона (внутри
строкового литерала — тоже через один), а вставка ложится сразу после `foo`.

## Примеры

Вставить вызов в конец тела функции:

```markdown
# match cpp
    ...
    void RegisterFeatures(FeatureList* list) {
      list->Add(kFastPath);
    >>>
    }
    ...
# end
# patch

      list->Add(kNewPath);
# end
```

Читается так: *пропусти что угодно, найди заголовок этой функции, затем этот
вызов, **вставь здесь**, а сразу следом обязана идти закрывающая `}` — дальше что
угодно до конца файла.* `}` здесь не украшение: именно она удерживает вставку
**внутри** этой функции (см. третье правило ниже).

Заменить диапазон — всё между `>>>` и `<<<` это старый код, он обязан совпасть и
в выход не идёт:

```markdown
# match cpp
    ...
    namespace content {
    ...
    >>>
    void RegisterFeatures( ... ) {
    <<<
    ...
# end
# patch
    // Registers every content feature.
    void RegisterFeatures( FeatureList* list ) {
# end
```

Обрати внимание на `...` **внутри** якоря: нутро сбалансированной скобочной пары
можно пропустить, и якорь переживёт правку списка аргументов. `generate` по
умолчанию так якоря и пишет.

## Установка

hatch выходит в трёх видах. Каждый ставится отдельно и нужен для своей задачи:

| что | для чего | что нужно в системе |
|---|---|---|
| [расширение VS Code](https://github.com/Danil-Varakin/HatchVSCodeExtension-) | писать патчи и видеть, куда ложится каждый ханк, прямо в редакторе | ничего: hatch и грамматики внутри расширения |
| `hatch-apply` | накладывать патчи при сборке проекта | ничего: Node и грамматики внутри файла; `git` — если база берётся из git |
| `hatch` (CLI) | `generate`, `apply`, `init` в терминале, скриптах и CI; API для своих инструментов | Node.js 22 или новее; `git` — если версии берутся из git |

Все три проверяются в CI на Linux, macOS и Windows.

**Расширение VS Code.** Файл `hatch-vscode-<версия>.vsix` со страницы
[Releases расширения](https://github.com/Danil-Varakin/HatchVSCodeExtension-/releases);
в VS Code: **Extensions** → **…** → **Install from VSIX…**. Подробно — в README расширения.

**`hatch-apply`.** Один исполняемый файл на платформу (linux-x64, linux-arm64,
darwin-arm64, win-x64) на [странице Releases hatch](https://github.com/Danil-Varakin/hatchTs/releases).
Как скачать, проверить контрольную сумму и вызвать — в разделе
[«Применение патчей при сборке»](#применение-патчей-при-сборке-hatch-apply).

**`hatch` (CLI).** В реестре npm пакета нет; к каждому релизу на той же странице приложен
архив `hatch-<версия>.tgz`, и npm ставит его по адресу:

```bash
npm i -g https://github.com/Danil-Varakin/hatchTs/releases/download/v<версия>/hatch-<версия>.tgz
```

Появляется команда `hatch`; грамматики всех языков уже внутри, ничего не докачивается. Из
клона репозитория она работает и без установки: `npm run hatch -- <команда>`.

## Использование

```bash
# apply
hatch apply --match changes.hatch --in src/main.cpp --out src/main.cpp

# ...или пропатчить файл таким, каким его держит git: ляжет ли патч на master?
hatch apply --match changes.hatch --in src/main.cpp --branch master --verify

# generate
hatch generate --in new.cpp --in-old old.cpp --out changes.hatch   # файл: у пути есть расширение

# ...или взять старую версию из git: тот же файл на момент последнего коммита
hatch generate --in src/main.cpp --head --out changes.hatch

# ветка (её последний коммит), конкретный коммит, другой путь внутри репозитория
hatch generate --in src/main.cpp --branch master --out changes.hatch
hatch generate --in src/main.cpp --commit 1f3ac9d --out changes.hatch
hatch generate --in src/main.cpp --branch master --commit 1f3ac9d \
               --repo-path src/legacy/main.cpp --out changes.hatch

# hatch.config.json в корне репозитория
hatch init
```

`hatch` без аргументов печатает список команд, `hatch <команда> --help` — её опции,
`hatch --version` — версию инструмента и версию схемы конфига.

Коды выхода (на них можно опираться в скриптах):
`0` ок · `1` ошибка вызова или иной отказ · `2` разбор `.hatch` · `3` не легло ·
`4` неоднозначно · `5` конфиг · `6` грамматика · `7` нет изменений · `8` не привязать
правку (подробно — в «Кодах выхода» ниже).

### Опции `apply`
```
--match, -m <файл.hatch>   патч                                       [обязательно]
--in,    -i <файл>         файл, к которому применяется патч. Не указан — файл из
                           поля Target патча: от корня upstream проекта (конфиг
                           ищется вверх от патча), без upstream — от корня
                           репозитория, в котором лежит патч. Читается с диска.
                           Если указан --head, --branch, --commit или --repo-path,
                           из --in берётся только путь, содержимое приходит из git,
                           и файла на диске может не быть
--head,   -H               файл из git: последний коммит текущей ветки, путь из --in
--branch, -b <ветка>       файл из последнего коммита этой ветки, локальной или
                           удалённой. Тег или sha вместо ветки — вопрос перед чтением
--commit, -c <ревизия>     файл из этого коммита: sha, тег, HEAD~3. Вместе с
                           --branch коммит должен лежать в этой ветке, иначе вопрос
--repo-path  <путь>        читать из git этот путь вместо пути из --in; путь от
                           корня репозитория. Результат по-прежнему называется по --in
--eol <repository|worktree>
                           окончания строк файла из git: как хранит git (по
                           умолчанию) или как у --in на диске (для core.autocrlf)
--out,   -o <путь>         куда записать результат   [обязателен, кроме --dry-run и --verify].
                           Существующая папка или путь со слешем на конце — внутрь
                           пишется <имя --in>; любой другой путь — имя файла, он
                           перезаписывается. Недостающие папки создаются,
                           относительный путь — от корня репозитория, `-` — stdout.
                           Файл, в котором уже лежит этот результат, не
                           перезаписывается, и время его изменения не меняется.
                           Запись поверх --in, взятого из git, сначала спрашивает,
                           если в --in есть правки, которых нет в версии из git
--language, -l <язык>      язык файла; иначе — из `# match <язык>` патча, иначе — по
                           расширению --in
--dry-run                  напечатать правки, которые внёс бы патч; ничего не писать
--verify                   проверить, ложится ли патч: ответ — только код выхода
                           (0 — ложится), ничего не пишется. Патч проверяется на
                           версии из git: по флагам выше, иначе по generate.base
                           конфига. Без них в терминале hatch спрашивает, считать ли
                           базой файлы на диске; без терминала — отказ
--base-from-disk           с --verify: база — файлы на диске, без вопроса
--config <файл>            этот конфиг вместо найденного вверх от патча
--no-config                не читать конфиг; --in тогда обязателен
--log [место]              писать подробный лог в файл с правами 0600. Место —
                           папка или путь со слешем на конце: внутри создаётся
                           файл с новым именем на каждый запуск. Иначе место —
                           имя файла, он перезаписывается. Без значения — ./hatch-logs/
--yes,   -y                ответить «да» на все вопросы заранее. Без --yes и без
                           терминала ответ — «нет», и запуск останавливается
--help,  -h                справка
```

--in-old     <файл>        старая версия: файл на диске
--head,   -H               старая версия из git: последний коммит текущей ветки,

--branch, -b <ветка>       старая версия из последнего коммита этой ветки, локальной

--commit, -c <ревизия>     старая версия из этого коммита: sha, тег, HEAD~3. Вместе

--repo-path  <путь>        старая версия — этот путь в git вместо пути из --in; путь

                           окончания строк старой версии из git: как хранит git (по
                           умолчанию) или как у --in на диске (для core.autocrlf)

                           <имя --in>.hatch; путь на .hatch — сам файл, он

--language, -l <язык>      язык файла; иначе — по расширению --in

                           пробелы внутри строки не учитываются, состав строк — да
--agreement, -a            показывать каждый ханк по мере синтеза: Enter оставляет
                           его, n открывает редактор, чтобы написать ханки вручную.
                           Отказ от редактора или конец ввода останавливает запуск,
                           .hatch не пишется. Ответы можно подать через stdin, по
                           строке на ханк
--parents <n|all>          не больше n охватывающих блоков в шаблоне (all)
--min-parents <n>          не меньше n охватывающих блоков в каждом шаблоне (1)
--require-parents          если правку не привязать ни к одному охватывающему
                           блоку — отказ, а не шаблон без структуры
--parent-detail <n>        сколько уровней скобок в заголовках охватывающих блоков
                           пишется дословно, считая снаружи: 0 — `foo( ... )`,
                           1 — `foo(bar( ... ))` (0)
--min-siblings <n>         не меньше n соседних значащих строк с каждой стороны
                           правки в каждом шаблоне (0)
--siblings <n>             не больше n соседних значащих строк с каждой стороны (8);
                           0 — соседние строки не используются
--sibling-detail <n>       сколько уровней скобок в соседних строках пишется
                           дословно, считая снаружи (0)
--bridge-gap <n>           правки, между которыми не больше n неизменённых
                           непустых строк, объединяются в один ханк (0)
--config <файл>            этот конфиг вместо поиска; путь не ограничен
                           репозиторием, так один конфиг служит нескольким
--no-config                не читать конфиг: только встроенные значения и флаги
--print-config             напечатать итоговые настройки, файл конфига и источник
                           каждого значения (встроенное, конфиг, флаг) и выйти
--debug,  -v               трейс синтеза в stderr: каждый сегмент правки, каждая
                           проба привязки и выбранный ханк

                           перезаписывается. Без значения — ./hatch-logs/

                           терминала ответ — «нет», и запуск останавливается

В скобках — значение по умолчанию. Опции привязки и `--out`, `--language`, `--exact`,
`--head`, `--branch`, `--commit`, `--eol` можно закрепить в конфиге (см. «Конфигурация»).

### Версия файла из git

Флаги `--head`, `--branch`, `--commit`, `--repo-path` работают одинаково в `generate`
(старая версия) и в `apply` (файл, к которому применяется патч). Версия задаётся тремя
**независимыми координатами**; любую можно опустить, и она берёт значение по умолчанию:

| координата | флаг | если не указана |
|---|---|---|
| ветка  | `--branch` | та, в которой мы сейчас |
| коммит | `--commit` | последний коммит этой ветки |
| путь   | `--repo-path` | путь из `--in` внутри репозитория |

Все три опущены — это тот же файл на момент последнего коммита; чтобы попросить его, нужен
`--head`. `--branch master` — последний коммит `master`, `--commit 1f3ac9d` — тот же файл
из этого коммита, `--repo-path` подменяет файл, не меняя коммит.

Коммит называет версию сам по себе и берётся как есть. `--branch` рядом с `--commit` —
утверждение, что коммит лежит в этой ветке; если это не так, hatch спрашивает, прежде чем
читать. `--branch` принимает только ветку: о теге или sha спросят и укажут на `--commit`.
`--repo-path` принимает только файл: каталог — отказ.

`--in-old` — путь на диске, и его дополняет оболочка; `--repo-path` — путь в репозитории,
и его находит git.

### Сколько контекста несёт ханк

Опции привязки выбирают между двумя видами отказа. Больше охватывающих блоков и меньше
соседних строк — привязка **структурная**: она переживает правку соседних строк чужим
коммитом, потому что незакрытая `{` упорядочивает поиск, а её закрывающая скобка держит
правку внутри блока. Меньше блоков и больше соседей — якорь короче и читается легче, но
сползает вместе с соседями.

Неоднозначность hatch сначала снимает детализацией: раскрывает по одной скобке — ту, что
действительно сокращает число мест, где якорь может начаться, — и останавливается, когда
ни одна скобка не помогает. Потолка у этого нет. Только потом он добавляет соседние строки.

`--parent-detail` и `--sibling-detail` задают, сколько скобок раскрыто во всех ханках
сразу. Длинный якорь не теряет однозначности, но чаще ломается, когда upstream меняет
аргументы. Из одной пары версий этот размен не измерить, поэтому он настраивается, а не
выбирается автоматически.

### Настройки под задачу и язык

Встроенные значения — лучший общий выбор на всех языках из таблицы «Поддержка языков»:
лестница сама берёт столько родителей и соседей, сколько нужно для однозначности, обычно
одного соседа. Менять их стоит под конкретный риск — что именно upstream будет делать с
кодом вокруг патча.

| задача | в `hatch.config.json` | что выигрываете | чем платите |
|---|---|---|---|
| общий случай | ничего | патч переживает новый аргумент у соседа и у функции, переотступ, вставку и перенос блоков (кроме Python и YAML — ниже) | переименование родителя или строки над правкой — отказ |
| в коде есть копии: генерированный код, одинаковые методы в разных классах | `"parents": { "min": 99 }` | копия функции в другом месте никогда не принимается за свою | переименование любого охватывающего блока (функции, класса, namespace) — отказ |
| upstream часто переименовывает функции и классы | `"siblings": { "min": 2 }` | переименование контейнера переживается вдвое чаще | правка строки через одну над правкой — отказ |
| короче и читабельнее ханк | `"parents": { "detail": { "base": 1 } }` | заголовки родителей с аргументами: в C++ шаблон короче на пятую часть | новый параметр функции или переименованное условие — отказ |
| upstream часто меняет аргументы | ничего (`detail.base` 0) | `foo( ... )` переживает новый аргумент | — |

Чего не делать:

- `"parents": { "max": 1 }` или `2` — на повторяющемся коде (одинаковые тела функций)
  `generate` отказывает с неоднозначностью;
- `"siblings": { "max": 0 }` — строку, добавленную в середину блока, не к чему привязать:
  без соседей ставится только правка у края блока, где соседа заменяет закрывающая скобка;
- `"siblings": { "detail": { "base": 1 } }` — новый аргумент у соседней строки, то есть
  самая частая правка upstream, — отказ.

`exact` на привязку не влияет: он решает, сравнивать ли пробелы, а не где якорь.

Что зависит от языка:

| язык | что пишется в якоре дословно | рекомендация |
|---|---|---|
| C++, Java, JavaScript, TypeScript | имена; аргументы и условия — `( ... )` | встроенные значения |
| Go, Rust, Kotlin, IDL | условие блока (`if ctx.ready {`, `group ready {`) | встроенные значения; переименованное условие — отказ при любых настройках |
| Python | условие блока (`if ctx.ready:`) | встроенные значения; переименованное условие — отказ при любых настройках; блок, сменивший место среди соседей (перенесён, поменялся с соседом, рядом встал новый), может лечь не туда без ошибки — при любых настройках |
| YAML | строки как есть; читается как текст, отступ блоков не образует | встроенные значения; как в Python, блок, сменивший место среди соседей, может лечь не туда без ошибки |
| HTML, XML | значения атрибутов в заголовках и соседних строках | встроенные значения; правка атрибута рядом с патчем — отказ при любой детали |
| JSON | ключи | встроенные значения; переименованный соседний ключ — отказ |
| CSS | селектор; аргументы — `( ... )` | встроенные значения |

Ключи одного конфига действуют на все языки проекта. Настройку для одного языка задают
флагом на запуск или отдельным конфигом (`--config`).

Числа и стенд — `npm run bench -- --case tuning` (одна модель кода в 18 языках, глубина
вложенности 1–3, уникальные / повторяющиеся / клонированные тела, правка в середине и в
конце блока, 22 вида правки upstream); утверждения этого раздела держит
`test/unit/tuning.test.ts`.

### Ханк вручную

Когда синтез не может привязать правку — например, есть два одинаковых места, — а за
терминалом человек, `generate` объясняет причину и открывает редактор (`$VISUAL`, иначе
`$EDITOR`, иначе `vi` / `notepad`). В редакторе — `.hatch` на этот момент: **все** ханки,
заготовка ханка для этой правки и сама правка, процитированная сверху. Вернувшийся текст
проверяется: файл должен разобраться, и каждый ханк должен лечь на старую версию по
порядку. Если нет — причина встаёт сверху, и вопрос повторяется; ответ «нет» останавливает
запуск без `.hatch`, а отредактированный файл сохраняется (путь печатается). Когда всё
сходится, синтез продолжается от текста, который дают эти ханки. Если тело патча после
правки расходится с `--in`, оно остаётся как есть, а запуск кончается предупреждением.

Без терминала — скрипт, CI — `generate` завершается с кодом 8.

Через сервис (расширение редактора) тот же круг — это `detail.draft` из `SynthesisError`,
отправленный обратно параметром `keep` у `generate`; см. [PROTOCOL.md](./PROTOCOL.md).

### Когда hatch спрашивает, прежде чем продолжить

Некоторые запросы git выполнить может, но они, возможно, говорят не то, что имелось в
виду. О них **спрашивают**: предупреждение говорит, что значит продолжить.

| ситуация | продолжить значит |
|---|---|
| `--commit` не лежит в названной рядом `--branch` | коммит читается из истории, которой у ветки не было |
| `--branch` называет тег или sha | он читается как обычная ревизия, как с `--commit` |
| `apply` пишет поверх `--in`, взятого из git, а в файле есть правки, которых в той версии нет | на его место ложится пропатченная версия из git; незакоммиченные правки теряются |
| `generate` пишет патч туда, где уже лежит патч другого файла | тот патч перезаписывается |

```
warning: commit 1f3ac9d is not on branch main — going ahead reads that commit all the
same, out of a history branch main never had
  go ahead? [y/N]
```

По умолчанию — **нет**. `--yes` / `-y` отвечает «да» заранее. Без терминала — труба, CI —
ответ «нет», и запуск останавливается с подсказкой про `--yes`.

То, чего git не может выполнить вовсе — ветки, коммита или файла нет, на месте файла
каталог, git не запускается, — всегда отказ, и `--yes` этого не меняет.

### Конфигурация

`hatch.config.json` закрепляет настройки `generate` для проекта, чтобы не повторять флаги
в каждом запуске. Создаётся командой `hatch init` (опции — выше).

- Формат — JSON без комментариев и висячих запятых.
- Приоритет: встроенные значения < `hatch.config.json` < флаги командной строки.
- Конфиг выбирается по порядку, берётся первый найденный:
  1. `--config <файл>`;
  2. `hatch.config.json` вверх по папкам от `--in` (у `apply` — от патча) до корня
     репозитория; в домашнюю папку поиск не заходит;
  3. конфиг, чей `upstream` содержит файл, — в подпапках корней репозиториев на пути вверх
     и в папках выше репозитория (см. «Проект поверх чужого кода»); два таких — ошибка с
     именами обоих;
  4. файл из `$HATCH_CONFIG`;
  5. `hatch.config.json` в текущей папке, если его `upstream` содержит файл.
- `apply` берёт из конфига только `upstream` (откуда считать путь `Target`) и
  `generate.base` (база для `--verify`). Как читается патч, конфиг не меняет: `.hatch`
  значит одно и то же на любой машине.
- Неизвестный ключ, значение не того типа, отрицательное или дробное число — отказ с
  кодом 5, в сообщении назван ключ.
- Пишите только ключи, которые отличаются от встроенных значений: тогда улучшенное
  умолчание следующей версии hatch дойдёт до проекта.
- Итоговые настройки и источник каждой — `hatch generate --in src/a.cc --print-config`.

#### Ключи конфига

| ключ | значение | по умолчанию | флаг | назначение |
|---|---|---|---|---|
| `$schema` | URL | — | — | Адрес JSON Schema той версии, которую называет `version`. Нужен только редактору — для подсказок и проверки при вводе; hatch его не читает |
| `version` | целое, сейчас `2` | новейшая, которую читает hatch | `init --config-version` | Версия схемы, по которой написан файл; ключи проверяются по ней. Версия новее, чем знает hatch, — отказ с просьбой обновить hatch |
| `upstream` | путь или `null` | `null` | `init --upstream` | Корень чужого кода, к которому проект пишет патчи; путь от папки конфига. С ним `generate.out` обязан быть папкой, и патчи раскладываются в ней по путям файлов от этого корня |
| `generate.out` | путь или `null` | `null` | `--out` | Куда записывается `.hatch`. `null` — рядом с исходным файлом. Значение без расширения или со слешем на конце — папка, патч в ней называется `<имя файла>.hatch`; значение на `.hatch` — сам файл; другое расширение — отказ. Относительный путь — от корня репозитория, а с `upstream` — от папки конфига |
| `generate.language` | имя языка или `null` | `null` | `--language` | Язык файлов. `null` — по расширению. Нужен, когда расширение указывает не на тот язык: например, `.h` с кодом на C (`.h` по умолчанию — C++) |
| `generate.exact` | `true` / `false` | `false` | `--exact` | `true` — патч воспроизводит новый файл байт в байт. `false` — строки сравниваются после нормализации: отступы и пробелы внутри строки не учитываются, состав и порядок строк учитываются |
| `generate.bridgeGap` | 0–1000 | `0` | `--bridge-gap` | Две правки, между которыми не больше стольких неизменённых непустых строк, объединяются в один ханк. Больше значение — меньше ханков, каждый длиннее |
| `generate.parents.min` | 0–1000 | `1` | `--min-parents` | Сколько охватывающих блоков (функция, класс, namespace) как минимум входит в каждый шаблон. Охватывающий блок привязывает правку к структуре, и при правке соседних строк она не уйдёт в другую функцию. `0` разрешает шаблон без охватывающих блоков |
| `generate.parents.max` | 0–1000 или `"all"` | `"all"` | `--parents` | Сколько охватывающих блоков как максимум входит в шаблон. hatch добавляет их изнутри наружу, пока место правки не станет однозначным |
| `generate.parents.required` | `true` / `false` | `false` | `--require-parents` | `true` — если правку не удаётся привязать ни к одному охватывающему блоку, `generate` отказывает, а не пишет шаблон без структуры |
| `generate.parents.detail.base` | 0–1000 | `0` | `--parent-detail` | Сколько уровней скобок в заголовках охватывающих блоков пишется дословно, считая от внешних; остальное заменяется на `...`. `0` — `foo( ... )`, `1` — `foo(bar( ... ))`. Больше — легче читать, но шаблон чаще ломается при правке аргументов |
| `generate.siblings.min` | 0–1000 | `0` | `--min-siblings` | Сколько соседних значащих строк с каждой стороны правки как минимум входит в каждый шаблон |
| `generate.siblings.max` | 0–1000 | `8` | `--siblings` | Сколько соседних значащих строк с каждой стороны как максимум входит в шаблон. `0` — шаблон опирается только на структуру |
| `generate.siblings.detail.base` | 0–1000 | `0` | `--sibling-detail` | Сколько уровней скобок в соседних строках пишется дословно, считая от внешних |
| `generate.base.head` | `true` / `false` | `false` | `--head` | `true` — старая версия берётся из git: последний коммит текущей ветки |
| `generate.base.branch` | имя ветки или `null` | `null` | `--branch` | Старая версия — последний коммит этой ветки, локальной или удалённой. `null` — текущая ветка |
| `generate.base.commit` | ревизия или `null` | `null` | `--commit` | Старая версия — этот коммит: sha, тег, `HEAD~3`. Вместе с `branch` должен лежать в этой ветке. `null` — последний коммит ветки |
| `generate.base.eol` | `"repository"` / `"worktree"` | `"repository"` | `--eol` | Окончания строк версии из git. `"repository"` — как их хранит git; `"worktree"` — как у файла на диске. `"worktree"` нужен при `core.autocrlf=true`, иначе каждая строка выглядит изменённой |

Любой из ключей `generate.base.head`, `branch`, `commit` означает «старая версия из git».
Git-флаг в командной строке заменяет все три на этот запуск; `--in-old` их не учитывает.

#### Примеры: `out`, `base`, `upstream`

**`generate.out` — куда пишется патч.** Без него патч ложится рядом с файлом:

```json
{ "version": 2 }
```
```
repo/
├── src/net/http.cc
└── src/net/http.cc.hatch        hatch generate --in src/net/http.cc --head
```

Папка в `out` собирает все патчи в одном месте — плоско, по имени файла:

```json
{ "version": 2, "generate": { "out": "patches" } }
```
```
repo/
├── src/net/http.cc
└── patches/
    └── http.cc.hatch
```

Если у двух файлов одно имя (`src/net/http.cc` и `src/ui/http.cc`), их патчи претендуют на
одно место, и hatch спросит, прежде чем перезаписать. Чтобы такого не было, нужен
`upstream` (ниже).

**`generate.base` — с чем сравнивается файл.** Без него каждый запуск `generate` должен
получить `--in-old` или git-флаг. С ним — достаточно `--in`:

| `base` | старая версия | что описывает патч |
|---|---|---|
| `{ "head": true }` | последний коммит текущей ветки | незакоммиченные правки файла |
| `{ "branch": "main" }` | последний коммит `main` | всё, чем рабочий файл отличается от `main`, — например, правки ветки разработки |
| `{ "commit": "v1.0" }` | тег `v1.0` | всё, что изменилось с этого релиза |

```json
{ "version": 2, "generate": { "base": { "branch": "main" } } }
```

**`upstream` — патчи деревом.** `upstream` называет корень кода, к которому пишутся патчи,
а `out` — папку, где патчи повторяют пути файлов от этого корня. `"."` — корень — папка
конфига, то есть сам репозиторий:

```json
{ "version": 2, "upstream": ".", "generate": { "out": "patches", "base": { "head": true } } }
```
```
repo/
├── hatch.config.json
├── src/net/http.cc
├── src/ui/http.cc
└── patches/
    └── src/
        ├── net/http.cc.hatch    Target: src/net/http.cc
        └── ui/http.cc.hatch     Target: src/ui/http.cc
```

Когда патчи и код лежат в разных репозиториях, `upstream` указывает из папки конфига на
чужой код — например, `".."`; см. «Проект поверх чужого кода».

Что делает `generate` при разных `--out` (или `generate.out`):

| `--out` | куда пишет патч | `Target` |
|---|---|---|
| не задан | рядом с `--in`: `<in>.hatch` | от корня репозитория |
| `-` | stdout | — |
| `patches`, `patches/`, существующая папка | `<корень репо>/patches/<имя --in>.hatch` | от корня репозитория |
| `p.hatch`, `deep/p.hatch` | этот файл, от корня репозитория | от корня репозитория |
| `p.md`, `p.txt` | отказ, код 5 | — |
| абсолютный путь | как выше, от `/` | нет, если патч вне репозитория |
| с `"upstream"` и папкой | `<папка конфига>/<out>/<путь от апстрима>.hatch` | от корня апстрима |
| с `"upstream"` и `-` или без `out` | отказ, код 5 | — |

Относительный путь считается от корня репозитория, а не от текущей папки: одни и те же
настройки означают одно место в терминале, в редакторе и в CI. Вне репозитория — от папки
файла. Патч того же файла и файл, названный прямо (`--out x.hatch`), перезаписываются без
вопроса.

### Проект поверх чужого кода

Форк держит патчи в своём репозитории и правит код, в который сам не коммитит. Пусть
апстрим выкачан в `work/`, а проект лежит внутри него:

```
work/                         апстрим — репозиторий, куда вы не коммитите
├── src/ui/window.cc
├── third_party/zlib/         внутри — отдельный репозиторий
└── myfork/                   ваш проект — ваш репозиторий
    ├── hatch.config.json
    └── patches/
```

`work/myfork/hatch.config.json` говорит, где этот код:

```json
{ "version": 2, "upstream": "..", "generate": { "out": "patches", "base": { "head": true } } }
```

`upstream` — корень правимого кода **от файла конфига**. С ним патч для
`work/src/ui/window.cc` — это `work/myfork/patches/src/ui/window.cc.hatch`, а его
`Target` — `src/ui/window.cc`. База берётся из git-репозитория, ближайшего к файлу:
`work/third_party/zlib/...` читается из собственного репозитория zlib, без списка
репозиториев.

```bash
hatch generate --in work/src/ui/window.cc                   # найдёт конфиг myfork
hatch apply --verify --match work/myfork/patches/src/ui/window.cc.hatch
```

Конфиг файла находится по заявке: сначала вверх от файла до корня его репозитория; затем
в непосредственных подпапках каждого корня репозитория на пути вверх
(`work/*/hatch.config.json`) и в папках выше репозитория. Два конфига, заявляющих один
файл, — ошибка, в которой названы оба.

| раскладка | конфиг | `upstream` |
|---|---|---|
| проект внутри апстрима | `work/myfork/hatch.config.json` | `".."` |
| апстрим внутри проекта | `proj/hatch.config.json`, код в `proj/upstream/` | `"upstream"` |
| рядом | `ws/proj/hatch.config.json`, код в `ws/upstream/src/` | `"../upstream/src"` — запуск из `ws/proj` или `--config` / `$HATCH_CONFIG` |
| один репозиторий, патчи отдельным деревом | в корне репозитория | `"."` |
| один репозиторий, патч рядом с файлом или в одной папке | в корне репозитория | нет |

`hatch init --upstream ..` пишет такой конфиг.

### Коды выхода (для CI)
`0` успех · `2` ошибка разбора · `3` нет совпадения (показывает «самую глубокую»
точку, до которой дошёл шаблон) · `4` неоднозначно (показывает конкурирующие
позиции) · `5` негодная конфигурация · `6` грамматики нет или она не сошлась с
пином · `7` `generate` не нашёл, что менять: новая версия совпадает со старой после
нормализации (одни пробелы и пустые строки — не изменение), а с `--exact` — побайтно;
`.hatch` не записан · `8` `generate` не смог привязать правку: ни один шаблон вокруг неё не
ложится туда и только туда (в терминале сначала предлагается редактор) · `1` всё
остальное: неверный вызов, нет файла, отказ git, неизвестный язык, ответ «нет» на вопрос
или непредвиденный сбой.

`6` — отдельный код намеренно: он говорит, что в *сборке* нет грамматики или лежит не
та, что закреплена (`HATCH_GRAMMAR_DIR`), а не что с патчем что-то не так.

Неоднозначность — **ошибка**, а не молчаливый выбор: если шаблон ложится в двух
местах с разным результатом, будет код `4` и список позиций, а лечится это
добором контекста.

Когда патч не ложится, быстрее всего понять причину так: `--debug` у `generate`
показывает, как выбирались якоря, а `--dry-run` у `apply` — какие ровно правки
получились бы, не трогая файл.

## Применение патчей при сборке: `hatch-apply`

Сборке проекта не должны быть нужны Node, npm и сеть, чтобы наложить патчи на код. В каждом
выпуске есть `hatch-apply` — один исполняемый файл, внутри которого Node, рантайм
tree-sitter и все закреплённые грамматики, — для linux-x64, linux-arm64, darwin-arm64 и
win-x64, и рядом `SHA256SUMS`. Движок тот же, что у `hatch apply`: патч, который
`generate` сделал и который ложится в редакторе, ляжет и при сборке.

```bash
curl -LO https://github.com/Danil-Varakin/hatchTs/releases/download/v0.4.1/hatch-apply-0.4.1-linux-x64
curl -LO https://github.com/Danil-Varakin/hatchTs/releases/download/v0.4.1/SHA256SUMS
sha256sum -c --ignore-missing SHA256SUMS
install -m755 hatch-apply-0.4.1-linux-x64 tools/hatch-apply

tools/hatch-apply verify --match myfork/patches/src/ui/window.cc.hatch
tools/hatch-apply apply  --match myfork/patches/src/ui/window.cc.hatch
```

| | |
|---|---|
| `hatch-apply apply --match <патч> [--out <путь>]` | накладывает патч на его файл — без `--out` на месте |
| `hatch-apply verify --match <патч>` | то же без записи: код 0, если ложится чисто |
| `hatch-apply --version` | версия, Node внутри, пин каждой грамматики |

Файл — тот, что патч называет в `Target`, найденный через `hatch.config.json` проекта так
же, как его находит `hatch` (`--in` называет другой). База всегда чистая: из git —
`--head` / `--branch` / `--commit`, иначе `generate.base` конфига — или, с
`--base-from-disk`, файлы на диске как есть (и он предупреждает, что взял их так); это
должна быть чистая база, а не файлы, на которые патч уже наложен (см. «Известные
ограничения»). Без этого — остановка с кодом 5. Он **ничего не спрашивает**: то, о чём
спросил бы `hatch` (тег вместо ветки, коммит не из названной ветки), отклоняется с
объяснением. На месте
файл, где результат уже лежит, не перезаписывается — сборка его не перекомпилирует; файл
со своими изменениями — например, результат патча, который с тех пор поменялся, —
перезаписывается, и об этом сказано: код, который сборка патчит, проекту хранить не нужно.
Его флаги выбраны из флагов `hatch apply`, у каждого тот же смысл; генерации, сервиса и
загрузки в нём нет. Для базы из git нужен `git` в `PATH`.

## API

```ts
import { applyAll, synthesize, parseHatchFile, printHatchFile, adapterForLanguage } from 'hatch';

const adapter = adapterForLanguage('cpp');
await adapter.init();

const { source, edits } = applyAll(oldCode, parseHatchFile(md), adapter);
const md2 = printHatchFile(synthesize(oldCode, newCode, adapter), 'cpp');
```

### Функции

| | |
|---|---|
| `applyAll(source, file, adapter)` | применяет ханки по очереди; возвращает `{ source, edits }`. Бросает `MatchError` или `AmbiguityError` на первом ханке, который не лёг |
| `synthesize(old, new, adapter, options?)` | порождает `Hunk[]` из двух версий файла. Бросает `SynthesisError`, если правку не привязать |
| `generatePatch(request)` | весь `generate` одним вызовом, на тексте: `.hatch` с шапкой, предупреждения, связи. Бросает `NoChanges`, если менять нечего |
| `resolveHunks(source, file, adapter)` | куда ложится каждый ханк: патч, база и пропатченный текст рядом, отказ по каждому ханку вместо исключения |
| `parseHatchFile(text)` | `.hatch` → `HatchFile` |
| `printHatchFile(hunks, language?)` | `Hunk[]` → `.hatch` |
| `trailingSpaceWarnings(hunks)` | строки тела патча со значащими хвостовыми пробелами |
| `adapterForLanguage(name)` | адаптер по имени языка |
| `adapterForFile(path)` | адаптер по расширению файла |
| `supportedLanguages` | имена и синонимы языков реестра |

`adapter.init()` вызывается один раз и грузит грамматику; `buildMap` после этого
синхронный.

### Ошибки

`HatchError` — общий предок, у каждого наследника поле `exitCode`, совпадающее с
кодом выхода CLI: `ParseError` (2), `MatchError` (3), `AmbiguityError` (4),
`ConfigError` (5), `GrammarError` (6), `NoChanges` (7), `SynthesisError` (8), а также
`GitError`, `LanguageError`, `PathError` (1).

### Типы

`HatchFile`, `Hunk`, `MatchPattern`, `LanguageAdapter`, `ApplyResult`, `AppliedEdit`,
`SynthOptions`, `SynthEvent`, `Tracer`, `GenerateRequest`, `GenerateOutcome`,
`HunkLink`, `LinkFailure`, `LinkStatus`, `ResolveResult`, `Span`, `SynthesisFailure`.

### Границы

Экспортируется только перечисленное выше. Матчер, патчер, канонизатор, карта
исходника, `infra/` и содержимое папок языков — внутренние и меняются без
предупреждения; подпути (`hatch/dist/...`) закрыты полем `exports`.

`LanguageAdapter` доступен как тип: адаптер получают из реестра и передают
обратно. Написание своих адаптеров не поддерживается.

## Сервис: hatch для редактора

`node node_modules/hatch/dist/bin/service.js` запускает hatch долгоживущим процессом,
который говорит JSON по stdio: `generate`, `resolve` и `apply` над текстом вместо
файлов, и координаты каждого ханка в базе и в пропатченном тексте. С ним говорит
расширение VS Code. Контракт и то, как сверяется его версия, — в
[PROTOCOL.md](./PROTOCOL.md) (на английском); типы опубликованы как `hatch/protocol`.

## Грамматики

Разбор делает tree-sitter, поэтому каждому языку нужен свой `.wasm`. Грамматики **идут
внутри hatch** — около 17 МБ на все, 1,7 МБ в упакованном архиве, — и во время работы
ничего не скачивается. Каждый язык пинует свою грамматику в собственной папке:

```ts
grammar: {
  file: 'tree-sitter-go.wasm',
  package: 'tree-sitter-go',
  version: '0.25.0',
  sha256: '9504573f352b20be7f2f1911754d710622aedc15afff16d5ed8fb5645681aee7',
},
```

и байты обязаны совпасть с пином, где бы файл ни нашёлся: `.wasm` — исполняемый код, а
другая грамматика может положить ханк в другое место (F3), поэтому файл с другим sha256
роняет запуск (код `6`). Грамматики нет совсем — это сбой сборки, так и сказано.

| Переменная | Действие |
|---|---|
| `HATCH_GRAMMAR_DIR` | искать сначала здесь — работа над ядром, своя сборка; пин всё равно проверяется |

В репозитории грамматик нет: `npm run grammars` (`scripts/fetch-grammars.ts`) кладёт
закреплённые в `grammars/`, его запускают `npm test` и `npm pack`.
`node --experimental-strip-types scripts/fetch-grammars.ts --pin <пакет@версия>` печатает
блок для `index.ts` нового языка.

## Три правила, зафиксированные волевым актом (из синтаксиса не выводятся)

Они осознанные и стабильные; патчи на них опираются:

1. **`<<<` заменяет ВКЛЮЧИТЕЛЬНО.** Литералы между `>>>` и `<<<` — это «старый
   код»: обязаны совпасть, но в выход не идут — их место занимает тело патча.
   Литералы *снаружи* меток — контекст, сохраняются.
2. **Шаблон описывает файл целиком.** `...` — единственный способ что-то
   пропустить. Нет ведущего `...` — первый якорь стоит со смещения 0; нет
   хвостового — последний якорь кончается на EOF.
3. **Незакрытая `{` упорядочивает, но не запирает.** Совпавшая открывающая скобка
   означает лишь «следующий якорь — после неё»: поиск всё равно идёт до конца
   файла, и «побег» из блока легален. Чтобы удержать правку **внутри**
   конструкции, в шаблоне надо написать её закрывающий токен. Поэтому `generate`
   выдаёт и заголовок охватывающей функции, и её `}`. В Python у блока закрывающего
   токена нет: его закрывает следующая строка его уровня, и она же закрывает все
   вложенные в него блоки — `class Archive:` на колонке 0 разом кончает и метод, и
   класс перед собой.

## Известные ограничения

Чего hatch не делает — намеренно или пока, — и что стоит знать заранее:

- **Одинаковый код с одинаковым окружением не различить.** В языке шаблонов нет
  «n-го вхождения»: если два места совпадают слово в слово вместе с соседями,
  `generate` сообщит о неоднозначности, а `apply` выйдет с кодом `4`. Такой якорь
  пишется руками — с опорой на отличающийся код, часто на тот, что идёт *после* правки.
- **«Уже применено» не распознаётся — его исключает порядок работы.** hatch не проверяет,
  есть ли патч в файле: нашёл место — пишет. Наложенный второй раз на собственный
  результат, патч может повторить вставку с кодом 0 — `... void g() { ... >>> } ...`
  по-прежнему находит конец `g()`; на не том файле обычно выходит код `3`. Поэтому каждый
  запуск, который что-то решает, начинается с чистой базы: `apply --verify` и
  `hatch-apply` читают файл из git (`--head`, `--branch`, `--commit` или `generate.base`),
  а `generate` проверяет каждый ханк на той старой версии, что ему дали. Патчить файлы
  на диске (`hatch apply` без git-координаты, `--base-from-disk`) можно только когда они и
  есть эта чистая база, — никогда файл, на который патч уже наложен.
- **Окончания строк принадлежат файлу, а не патчу.** Патч пишет строки с окончанием той
  строки, где начинается правка, поэтому перевести CRLF-строки в LF (и обратно) патчем,
  начинающимся на CRLF-строке, нельзя.
- **Git с `core.autocrlf=true`** (умолчание Git for Windows): версия из git приходит с
  окончаниями, которые хранит репозиторий (LF), а файл на диске — с CRLF, и
  `generate --head --exact` видит изменённой каждую строку. Добавьте `--eol worktree`
  (или `generate.base.eol: "worktree"` в конфиге) — версия из git придёт с окончаниями
  файла на диске; либо поставьте для репозитория `core.autocrlf false` (так велит и
  настройка Chromium под Windows), либо передайте старую версию через `--in-old`.
- **Большие файлы из почти одинакового кода замедляют `generate`** — от секунд до минут
  там, где один шаблон приходится примерять к множеству похожих мест.
- **При записи файла сохраняются права и запись идёт сквозь симлинк**, но не владелец,
  ACL и расширенные атрибуты, а жёсткая ссылка на файл отделяется — запись идёт через
  временный файл и переименование, чтобы прерванный запуск не оставил полфайла.
- **Пробелы внутри многострочного строкового литерала не значимы** (см. «Язык»), а
  `.mm` читается грамматикой Objective-C (см. «Поддержка языков»).

| Shell | `.sh` `.bash`, `postinst`, `postrm`, `preinst`, `prerm` | `shell`, `sh`, `bash` |
| YAML | `.yaml` `.yml` | `yaml`, `yml` |
| TOML | `.toml` | `toml` |
| Text | `.txt` | `text`, `txt` |

`generate` пишет в заголовок собственное имя языка — первое в последней колонке
(`cpp`, `objc`, `python`), как бы язык ни был выбран. Любое расширение из таблицы без
точки — тоже имя: его писал hatch 0.2.0 и старше (`# match mm`), и такой `.hatch`
применяется так же.

Структура берётся из tree-sitter, поэтому ветки препроцессора, raw-строки, макросы
и дженерики (`Map<K, V>` — пара скобок, `a < b` — нет) не путают сопоставление.
`.h` считается C++ по конвенции Chromium. `.mm` — это Objective-C++, которого не
покрывает полностью ни одна грамматика tree-sitter: лучше всех справляется
грамматика Objective-C, а на чисто C++-участках структура беднеет до текстового
сопоставления.

В HTML и XML блок — элемент с обоими тегами: открывающий тег вместе с атрибутами —
его заголовок, закрывающий тег — закрывашка: `<div id="a">` … `</div>` как `{` … `}`.
Элемент без закрывающего тега (`<img>`, незакрытый `<p>`) и `<br/>`, `<tag/>` блоком
не считаются. `<script>` и `<style>` — блоки, содержимое которых — текст. Внутри
значения атрибута в кавычках пробел — данные, как в строковом литерале; в остальных
местах он свободен.

В CSS блок — `{` … `}` правила или at-правила, заголовок — селектор или `@media (…)`.
Пробел между двумя селекторами — комбинатор потомка, поэтому он сохраняется: `.a .b` и
`.a.b` — разные якоря. В JSON блок — объект или массив, заголовок — ключ, значением
которого он является (`"permissions": [`); у объекта внутри массива своего заголовка нет.
JSON5 читается грамматикой JavaScript; там у объекта внутри массива заголовок — его первая
пара (`{ name: "AIPromptAPI",`). `DEPS` и Starlark (`.star`) по синтаксису — Python и
читаются как Python.

IDL, Mojom, Protocol Buffers, shell, YAML, TOML и простой текст hatch читает без
грамматики, как текст. Блок — пара `()`, `[]` или `{}`, сбалансированная вне строк и
комментариев формата, заголовок — то, что стоит перед открывающей скобкой (`interface X {`,
`message M {`, `f() {`); `if … fi` в shell и отступы YAML блоками не считаются. В shell,
YAML и тексте отступ строки сохраняется, как в Python. Файл другого расширения выбирается
по имени: `--language shell`, `--language text`.

### Как добавить язык: правило одной папки

**Язык — это одна папка в `src/lang/` и один `index.ts` в ней, где лежат ВСЕ его
правила: какую грамматику грузить, какие расширения считать своими, как
балансировать вложенность (`blockOf`) и как канонизировать текст литерала
(`normalize`). Правила языков НЕ выносятся в общий модуль — даже когда у двух
языков они записались бы дословно одинаково.**

Что это даёт: чтобы добавить язык, вы копируете одну папку и правите один файл,
ничего не зная про остальные и ничего в них не задевая. Видимое дублирование —
осознанная цена, и на практике правила расходятся: наборы скобочных пар у C, Go,
JavaScript и Python уже разные, а Kotlin требует своего определения того, где
начинается заголовок блока. Общий модуль «правил C-подобных» превратил бы каждое
такое различие в флаг.

Общим остаётся только язык-НЕЙТРАЛЬНОЕ: загрузка грамматики, обход дерева,
обвязка канона, сборка карты — то, чего язык не выбирает. Единственный общий файл,
который затрагивает добавление языка, — реестр адаптеров, и только потому, что
whitelist обязан быть статическим списком: имя языка приходит из недоверенного
`.hatch` и не должно превращаться в динамический импорт.

В `src/core/` при этом тоже не меняется ничего — это вторая проверка границы, и ни
одному языку из таблицы исключений не потребовалось. Python среди них стоит
особняком: значимый отступ, поэтому у него свой канонизатор и своё понятие блока,
где открывающий токен — двоеточие.

Грамматики лежат в `grammars/*.wasm`, их кладёт туда из официальных npm-пакетов
tree-sitter `npm run grammars`, и они идут внутри пакета.

## Структура проекта

```
src/
├── bin/        единственные файлы, которые что-то запускают: hatch (CLI), сервис, hatch-apply

├── lang/       всё языкозависимое: структура (tree-sitter) + нормализация
├── generate/   diff → сегменты → ханки → .hatch

└── index.ts    публичный API пакета
```

|---|---|

## Сборка и запуск

Исходники — `.ts`, исполняются напрямую на **Node 22+** через strip-types, поэтому
разработке шаг сборки не нужен. Пакет для публикации собирается (`npm run build` →
`dist/`), и именно эта сборка попадает в архив `npm pack`.

```bash
npm test          # юнит-, round-trip- и golden-наборы
npm run typecheck # tsc --noEmit по src/, test/ и bench/
npm run check     # то и другое
npm run build     # dist/, только для пакета
```

Разбор структуры — через **tree-sitter** (`web-tree-sitter`, WASM-грамматики:
кросс-платформенно, без нативной сборки); грузятся разово на старте. Рабочий
процесс и обоснование строгого tsconfig — в [CONTRIBUTING.ru.md](./CONTRIBUTING.ru.md).
